# Ciphered Private Bus (CPB): Appendix C, CDDL Schema and Size Analysis

- **Status:** Draft, baseline for gate G0. Companion to the
  [Protocol Requirements Specification](requirements.md) and
  [Appendix B, Wire Format](appendix-b-wire-format.md).
- **Date:** 2026-11-20
- **Author:** Evgenii Russkikh

## Abstract

This appendix gives a CDDL [RFC8610] schema for all 26 CBOR messages of Appendix B and their six sealed
bodies, the largest instance of every object with its encoded size, and the procedure that reproduces
these numbers. The largest instance of each object is generated by a script and validated with the
reference `cddl` tool, version 0.12.14. Every instance passes the schema and fits in a 16384-byte
frame. The deepest nesting is 4 (the passport) and the longest container holds 128 items.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT",
"RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as
described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown
here. The references cited in this appendix are listed in Section 16 of the requirements specification.

## C.1. Schema

The schema is the file [`cpb.cddl`](cpb.cddl) next to this document. It follows Appendix B; where
they disagree on a number, the numbers produced by the script of Section C.5 are correct (Appendix B,
Section B.1).

The schema covers the CBOR messages and the sealed bodies. The binary frames `StreamChunk` and
`BlobSegment` are not CBOR and are specified only by the tables of Appendix B, Section B.7.

The following constraints cannot be expressed in CDDL. They are stated as comments in the schema and
are covered by the test vectors of gate G2:

- the `versions` list in `Hello` and `PairInit` is strictly increasing;
- the length of `data` plus `pad` in a publication is at most 4096, and every byte of `pad` is zero;
- the relation between `size` and `seg` in a blob reference (Appendix B, Section B.5);
- `source_bytes ≤ bus_bytes` in a relay ticket;
- the `path` of a `RelayHello` has exactly `depth` items of the ticket, and `index` is below `2^depth`;
- the open fields of a `Relayed` message agree with the inner object they carry (Appendix B,
  Section B.10, rule 4 of the wrapped object), and `from` equals the alias of the link;
- the unused bits of `Passport.rights`, `StreamChunk.flags`, and `BlobSegment.flags` are zero.

Schema conventions:

- Integers are bounded everywhere, by `u53` (0 .. 2^53 - 1) or by `seq` (1 .. 2^31 - 1). Version
  numbers start at 1.
- A device key signature is `sig-p256` everywhere and a root signature is `root-sig`. The general type
  `signature` is used only for a call, which may be signed by the root key.
- Extension fields (keys 256..65535, R-FMT-14) are checked against the profile (`profile-val`), not
  admitted as `any`.
- In `Refusal`, fields 6 and 7 follow the order of the codes: 6 carries the sealing key claim (code 1),
  7 the nonce (code 2).

includes the message wrapper `{0: t, 1: bstr}` where the object travels inside a message. The headroom
is 16384 minus the size. Extension fields are not included: only the frame bounds them, and the
headroom shows how much room they have.

Sealed bodies are decoded separately, with their own depth count: relay access plaintext 4554 bytes
(depth 3, a list of pairs), reply plaintext 4395, command 4112, publication content 4109, join request
body 310, `PairDevice` 275, `PairBus` 219, `NodeInfo` 68; depth at most 2 in every other case. The deepest structure of the format is the passport: triple, `rest`,
permit list, permit, depth 4. The longest lists hold 128 items: permits, the relays of a checkpoint, and
the version lists of `Hello` and `PairInit`. A signed object is currently nested inside another object
at most one level deep (a sealing key claim in `Refusal`, a head in `HaltProof`); R-FMT-4 permits two.

A `Relayed` message adds at most 120 bytes to the frame it carries: the open fields of the publication
class at their largest, the 32-byte salt, the byte string header, and the 16-byte tag. Every object in
the table above, as the inner frame of a `Relayed` message, fits in the 16384-byte frame; the script
checks this for each of them. The largest inner frame is 16264 bytes, so a stream chunk or blob segment
sent through an external relay is at most 16262 bytes, header included.

[`tools/cddl/maxsize-output.txt`](../../tools/cddl/maxsize-output.txt).

### C.2.1. Halt Proof for Two Root Change Records

The largest halt proof is the closest object to the frame limit. It carries one head shared by both
records, which is the point of the proof (one number, two bodies). Layout at the largest generation,
2^31 - 1:

| Part | Bytes |
| --- | --- |
| Map header, `0: 12`, `1: 6` | 5 |
| Field 2, `head` as bstr: a map of the bus and the generation, 42 bytes | 45 |
| Fields 3 and 5, two hashes of `rest` | 70 |
| Fields 4 and 6, two lists `[K1, K2]`: 64 + 7856 bytes of signatures and 5 bytes of CBOR each | 15854 |
| **Total** | **15974** |

The signatures alone take 15840 bytes; CBOR and fields add 134. The size does not depend on the new
root key, because the proof carries only the hash of `rest`. The headroom therefore does not shrink if
the Root moves to a post-quantum key. A future hybrid root signature (P-256 and SLH-DSA) on two
checkpoints would give a proof of 15980 bytes, which also fits.

## C.3. Decisions Required by the Schema

Writing the schema forced a bound on every field. In the places listed below there was no bound, or one
concept had two encodings. Each decision can be reversed independently; all of them are reflected in
the requirements specification and Appendix B.

1. **Publication padding is bounded.** The source chooses the padding buckets and readers do not check
   them (R-CH-14), so without a bound `pad` could grow to 12 KiB and a channel of depth 16 would take
   three times the expected memory at readers and relays. The length of `data` plus `pad` is at most
   4096, and a non-zero `pad` byte rejects the publication. Rationale: the largest bucket equals the
   largest data, and every byte of content has exactly one valid encoding and one reaction to a
   violation.
2. **Channel key generation and ticket number are bounded.** Both are in the range 1 .. 2^31 - 1 of
   Section 13.1 of the requirements specification. A channel key changes when a reader is removed, on
   an epoch change, and on a reboot; this does not happen more than once a second, and 2^31 seconds is
   68 years.
3. **Stream credit has one encoding and a bound.** In `Command`, the stream request is two fields,
   3 `stream_mode` and 4 `credit`. Credit is written only in ordered mode and only when greater than
   zero; otherwise the field is absent, as in `Reply`. The bound is 1 .. 2^32 - 1, the width of the
   `credit` field in the chunk header: one quantity has one width.
4. **Blob segmentation is checked.** A publication header is rejected if `size` mod `seg` is in 1..16
   (the last segment would be shorter than the authentication tag and could never exist) or if
   ceil(`size` / `seg`) exceeds 2^31 - 1 (the 4-byte segment number is the AEAD nonce and must not repeat,
   R-KEY-9). With `seg = 16346` a blob can reach 32 TiB. Segment i starts at byte i × `seg` of the
   ciphertext for any `seg` in 1024..16346, because `seg` is one value for the whole blob and is in the
   signed header; resuming a download from any segment therefore works.
5. **No root change chain.** A root change record is accepted if it is signed by K1 and K2 and its
   generation is greater than the current one; the node moves to that generation at once. Nodes, the
   root device, and relays keep only the latest record, and `Get` has no generation field. A chain is
   unnecessary because every record is signed by K1 and K2, which are fixed in the bus identifier, not
   by the previous Root; TUF [TUF] requires walking every root version only because each one is signed
   by the keys of its predecessor. Properties are preserved: a fork of generation g (R-MEM-13) still
   reaches a node that skipped g, because whoever saw both records sends a `HaltProof` of kind 6, and
   rule 3 of Appendix B, Section B.3 does not discard root change proofs by generation. Stolen K1 and K2
   yield any generation at once regardless of a chain (L6).
6. **Defaults are explicit.** A field has a default value only if the schema marks it `.default`
   ([RFC8610], Section 3.8.6). In version 1 there is one such field, `flags` in the publication content.
   The check of R-FMT-2 thereby becomes mechanical.
7. **Minor bounds.** The `Reply` result code is 0..65535 (R-CALL-11). A device name is 1 to 64 bytes:
   an empty name cannot be shown to the owner. The first chunk of each stream direction is number 1,
   as in Section 13.1; blob segments are numbered from 0, because the segment number determines the
   offset.

The joiner's user-presence key is covered by `PairDevice.sig`: the signature is over
`SHA-256(encode(map of fields 1..3))`, that is, the device key, the user-presence key, and the name.
The Root rebuilds this map from the join request, and the strict CBOR profile makes the rebuild
unambiguous, including when the user-presence key is absent. A compromised acceptor can only replace
all of them with its own device key, which the fingerprint comparison detects (R-JOIN-7).

## C.4. Negative Examples

Negative examples show that the schema actually rejects something. The schema rejects: a `Get` for a
root change record with an extra field; a lossy-mode command with credit; a code 1 refusal carrying a
nonce; an unknown critical field; a root change halt proof with one signature; `seg = 1023`;
generation 0; a call `enc` one byte longer than the bound; version 0; an SLH-DSA signature in a join
request body and in a publication; a 36-byte reply ciphertext; a 292-byte pairing ciphertext; a ticket with tree depth 16; a relay
refusal naming both a bus and a bus alias; a relay hello carrying the fields of both sides; a wrapped
control object of a kind that is not a control-plane object; a wrapped publication without its depth;
a wrapped body one byte longer than the bound; and a
float, a negative integer, a boolean, and 2^53 in an extension field. It accepts extension field 300, as
it must. A passport with 129 permits is refused by the encoder itself.

The expected output is in
[`tools/cddl/negative-output.txt`](../../tools/cddl/negative-output.txt). These examples are the first
format vectors; gate G2 extends them to one vector per rule code.

## C.5. Reproducing the Check

The scripts are in [`tools/cddl/`](../../tools/cddl/). `maxsize.py` encodes CBOR itself under the
strict profile (shortest forms, ascending keys, the limits 2^53 - 1 and 128), builds the largest
instances, and validates each one with the reference CDDL tool. `negative.py` additionally needs the
Python package `cbor2`.

```sh
gem install cddl -v 0.12.14     # reference CDDL tool
python3 tools/cddl/maxsize.py   # sizes, depth, longest container; exit 1 on any schema failure
python3 tools/cddl/negative.py  # prints 'rejected' for every case except the extension field
```

Both outputs must match the committed files byte for byte; a difference means the schema, the script,
or Appendix B changed and the numbers in Appendix B and this appendix must be updated together.
