# cpb-sim

A deterministic in-memory simulator of **Ciphered Private Bus** (CPB) for application authors.

Several bus nodes run in one process, without a network and **without cryptography**. Each node
offers the application exactly the local interface of R-API-2 ([`cpb-api`](../cpb-api/)) and
follows the bus's membership, channel, call and stream rules, so application tests can run
multi-device scenarios (a root, commanders, readers, a member relay) without devices.

**Not a security boundary.** Nothing is encrypted or signed. The simulator shows the behaviour an
application sees at the interface and says nothing about secrecy.

## Where the rules come from

The `engine` modules are the Quint models of verification level V2 written as Rust, with the
same state and the same transitions:

| Engine | Model | What it covers |
| --- | --- | --- |
| `engine::channels` | [`models/channels`](../../models/channels/) | Channel keys and rotation, grants, publication numbers reserved in blocks, the reader's window and retention depth, the clearing publication, reboots |
| `engine::calls` | [`models/calls`](../../models/calls/) | Nonce slots, calls, replies, the two open refusals and the commander's automatic retries, "reset nonces", key epochs, passport changes |
| `engine::streams` | [`models/streams`](../../models/streams/) | A stream side in ordered and lossy mode, chunk numbers, credit in both directions, "end", "reset nonces" after a quiet period, the table of open streams |
| `engine::membership` | Section 6 of the specification | Passports and checkpoints, the validity rule, the halt on two records with one number |

**Trace equivalence.** `tests/replay.rs` replays model traces against the engines: every run of
the models' fixed scenarios and thirty random traces of the `small` instances, chosen so that
every action of each model is replayed. After every step
the engine's state, projected onto the model's variables, must equal the state the model reached.
The traces are generated by `tools/sim/gen_traces.py` from the pinned Quint with a fixed seed; a
CI job regenerates them and fails if they differ from the committed ones, so a model change that
the simulator does not follow is caught.

## The harness

- **Determinism** (R-VER-7). A run is fully determined by `Config::seed`.
- **Faults per hop.** Loss, duplication and reordering (`Faults`); `lose_in_flight` for a loss
  at a chosen moment; links up and down; a node asleep (`sleep`, `wake`); host events `reboot`,
  `reset_nonces` and `rotate_epoch`. A reboot also drops the events the application has not
  taken.
- **Routing.** A message goes over a direct link, or through one member relay (a valid member
  with the relay right) linked to both ends; the relay forwards it unchanged. Relay storage and
  quotas are not simulated. With `Config::relays_refuse_streams` a relay refuses every stream
  chunk, as R-STR-7 allows.
- **Owner operations.** `admit`, `change` and `revoke` act as the owner on the root device. A
  newly admitted device starts with the records it would receive at the end of enrollment.
- **Host requests.** A confirmation-class call or a call with the root key raises
  `Event::HostRequest`; the test answers it with `answer_host` (approve or refuse), standing in
  for the user (R-API-3).

## Errors

Every refusal carries its rule code from `cpb_api::codes`, the same list the core uses. The mode
follows the build type and is overridden by the environment variable `CPB_ERRORS=debug|release`
or by `Config::mode` (R-ERR-3). In debug mode every rejection of an incoming message is also
delivered as `Event::Rejected`; in both modes it is written to `Sim::log` with its code, kind and
detail (R-ERR-2).

## Decisions the simulator makes

These are interface behaviours the specification leaves open; the simulator fixes them and the
core follows the same choices.

- A new channel's readers are all valid members with the read right until `set_readers` says
  otherwise.
- `subscribe` delivers the channel's retained publications at once, as to a late joiner.
- On its own "reset nonces" a node also forgets the nonces it holds as a commander, so its next
  call starts with a nonce request instead of a stale nonce that would end as "outcome unknown".

## Blobs, node info and membership events

- **Blobs** (R-CH-15). `begin_blob`, `write_blob` in pieces of any size, and `finish_blob`
  publish a blob; the publication carries `BlobInfo` (size, segment count, segment size, and the
  header hash, for which the simulator computes a stand-in). `fetch_blob` takes any range of
  segments and returns a `FetchId`; the segments arrive in order as `Event::BlobSegment` and the
  end as `Event::BlobFetchFinished`. A fetch asks for its next segment only when the application
  has taken the previous event, so the application sets the pace; `cancel_fetch` stops it, and
  several fetches may run at once. The source serves a blob while it retains the publication, so
  a blob needs depth 1 or more; a fetch whose publication leaves retention ends with `blob/gone`.
  A fetch asks again for its outstanding segment when the link to the source comes back. The
  segment size is `Profile::blob_segment`, by default the 4096-byte segment frame of Section
  13.2 less the frame header and the authentication tag.
- **A new key on request** (R-CH-5, R-CH-6). `rotate_channel_key` marks an own channel exactly
  as "rotate key epoch" does for all of them, so it is the same transition of the channels
  model. Called before `set_readers` adds a reader, it keeps that reader from the past.
- **Node info** (R-CH-16). `set_name` and `set_app_info` publish the name and the application
  part on channel 0; every member receives `Event::NodeInfo`. Until `set_name`, a node's name is
  its device identifier, standing in for the name from pairing.
- **Membership** (R-API-2). Every accepted checkpoint or passport raises
  `Event::MembershipChanged`; `state()` then gives the members, the root generation, the
  checkpoint and the root device.

## Streams and calls

- **Opening** (R-STR-1). A call asks for a stream with `InvokeOptions::stream`: the mode and the
  commander's initial credit. The target sees the request in `Event::IncomingCall` and opens the
  stream with `reply_with_stream`, naming its own initial credit; a plain `reply` opens none. The
  commander gets its end in `CallOutcome::Replied`.
- **Data and credit** (R-STR-3, R-STR-4). `stream_write` sends one chunk, by default up to the
  4096-byte chunk frame of Section 13.2 less the chunk header and the authentication tag
  (`Profile::stream_chunk`). In ordered mode a write beyond the peer's credit sends nothing and
  returns `str/no-credit`; `stream_grant` adds credit and the peer sees `Event::StreamCredit`.
  In lossy mode there is no credit: the recipient holds `Profile::stream_buffer` bytes for its
  application and drops a chunk that does not fit.
- **Closing** (R-STR-5, R-STR-7). `stream_end` closes both sides. `Event::StreamClosed` gives
  every other reason: the peer's "end", link down, a quiet
  period between two "reset nonces", halt, revocation of either party, a chunk out of order, a
  chunk beyond the credit, and a stale side replaced by a new stream under the same number. A
  link down closes the streams that link carried, so behind a relay the far side learns of it
  only by the quiet period. A relay that does not serve streams raises `Event::StreamRefused`: an
  unsigned hint that the network can forge, so the stream stays open and the application decides.
- **Limit** (R-STR-6). `Profile::max_streams`, 8 by default, counts open streams and calls that
  asked for one. At its own limit a commander's `invoke` returns `str/too-many`; at the target's
  limit the core replies "too many streams" and existing streams stay.
- **Calls.** A reply carries a result code, a message for the log of up to 256 bytes, and data
  (R-CALL-10). `Event::IncomingCall` names the key that signed the call: the device key, the
  user-presence key, or the root key (R-CALL-4).

## Scope of this version

Membership without enrollment, channels, calls and streams. Enrollment (pairing and join
requests), root change by K1 and K2 with reissue, halt propagation, and power loss at every step
arrive next, together with the replay of the membership and enrollment models.
